# Fork update to v0.19.0

Prepared on 2026-11-17 in an isolated checkout. The live checkout and production
services were not advanced or restarted, and no production migrations were run.

## Source

- Fork baseline: `9051f11718788345158a38b5370c4abe0cdf7407`.
- Upstream release: `v0.19.0`, pinned to
  `f48bdf7a0c7dadc87f2eee73d2ab074d08a94035`.
- The fork's `f001`–`f005` migrations and legacy revision bridge stay in their
  existing positions. The combined graph has 118 migrations and one head, `113`.

The merge retains funding-domain management, transaction and recurring funding
choices, rule actions/previews, installment propagation, sync/import inheritance,
and credit-card payment allocations. Card statements keep their bill-cycle
filtering while other account summaries support upstream's reporting-date
override. Upstream's rule-pack provenance, provider settings, library and plugin
features are retained. Plugins remain disabled by default.

Funding-domain routes now have explicit `funding_domains:read` and
`funding_domains:write` token scopes. Regression tests cover read/write separation,
workspace binding, and rejection of reporting-date overrides on card purchases
without changing their funding assignment or statement totals.

  rejection, every installment, recurring generation and scoped domain access.

A private recovery snapshot was checksum-verified and restore-tested in a
separate PostgreSQL instance. Both the restored revision-105 database and an
empty database migrated to 113. Read-only inspection preserved the revision and
rows; the upgrade preserved every original column value across all 61 original
tables and introduced four tables. No existing transaction IDs needed re-keying
in this snapshot.

Fresh and restored schemas have matching columns, types, defaults and logical
constraints. The reviewed differences are equivalent text-array casts in 26
check constraints and one retained legacy index,
`ix_credit_card_payment_allocations_statement_due_date`. No required index or
constraint is missing. Column ordering is not treated as a schema mismatch.

## Deployment boundary

This source update does not deploy the release. Before a later deployment,
follow the [fork runbook](../fork-upstream-merge.md): stop writers, take a fresh
coordinated backup, build/recreate all enabled backend consumers, let the
one-shot migration service run, and verify data before resuming writers.

Existing environment provider credentials remain valid fallbacks; migration 113
does not move them into the database. Saved credentials depend on the matching
`SECRET_KEY`, and rollback past 113 needs the cleanup described in
[provider settings](../provider-settings.md). Code plugins remain optional and
require their own services and persistent-storage backup if later enabled.
